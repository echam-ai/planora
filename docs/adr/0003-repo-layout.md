# ADR 0003 — Monorepo layout and toolchain independence

- **Status:** Accepted
- **Date:** 2026-09-17
- **Depends on:** ADR 0001

## Context

ADR 0001 added a second deployable application. The repository currently holds a
single application at its root, generated by an external frontend-building
service, and that origin left several couplings in place:

- The entire Vite build is delegated to a vendored configuration package that
  bundles the plugin set, injects environment variables, sets path aliases, and
  targets Cloudflare by default — none of which is visible in the repository.
- The lockfile resolves several runtime dependencies from the vendor's private
  package registry rather than the public one, so every install, CI run, and
  Docker build fetches tarballs from third-party infrastructure.
- A module in the application reports caught React errors, together with the
  current route, to a global hook belonging to the vendor's editor preview.
- The served HTML carries the vendor's title, description, author, and social
  metadata.
- The package manifest, the package-manager configuration, the README, and the
  agent-instructions file all carry vendor-specific content, including a warning
  against rewriting history because the branch synchronizes back to the vendor's
  editor.

The frontend was built with an external tool as a one-time step. The tool is not
part of the product, is not intended to remain in the pipeline, and no reference
to it should persist in the repository, the dependency tree, the served
application, or the published history.

## Decision

### Monorepo with `apps/web` and `apps/api`

```
planora/
├─ docs/           specs, ADRs, runbooks
├─ deploy/         Compose files, reverse-proxy config, backup scripts
└─ apps/
   ├─ web/         TanStack Start application
   └─ api/         FastAPI application
```

A flatter alternative — keeping the web application at the root and adding a
top-level `api/` directory — was considered and initially preferred, because
moving the frontend breaks the vendor editor's expectation that the application
sits at the repository root.

That objection no longer applies: the vendor connection is being removed
entirely, so there is nothing left to keep compatible. With the constraint gone,
the symmetric layout wins on clarity — neither application is privileged, and
`deploy/` and `docs/` sit at the same level as the things they describe.

### Explicit build configuration

The vendored Vite configuration is replaced by an explicit plugin list:
TanStack devtools (development only, ordered first), `tanstackStart`, the React
plugin, the Tailwind plugin, `vite-tsconfig-paths`, and Nitro with the
**`node-server`** preset.

Two pieces the vendored package bundled are deliberately not reproduced: its
error-logger plugins and its sandbox port/host detection, both of which exist
only to serve the vendor's editor preview.

The preset change is required regardless of provenance. The bundled
configuration defaulted Nitro to a Cloudflare target, and the deployment target
is a VPS running Docker Compose.

The replacement plugin set was reconstructed from the vendored package's
declared peer dependencies and its own documentation, because dependencies had
never been installed in this working tree. The first successful production build
is the verification gate.

### Lockfile regenerated against the public registry

The lockfile is deleted and regenerated so every package resolves from the
public registry. This is a supply-chain fix, not a cosmetic one: the alternative
is a build pipeline whose inputs are fetched from a third party's cache
indefinitely.

The package-manager configuration's 24-hour minimum-release-age guard is kept,
because it is a genuinely useful supply-chain protection. Only the vendor-specific
exemptions to it are removed.

### Clean root commit

The two existing commits are discarded in favour of a single root commit
containing the finished tree, force-pushed over the remote. One of the existing
commit messages names the vendor, and one of the tracked files is a
vendor-specific prompt document; working-tree deletion alone would leave both
reachable in published history.

A local staging commit is taken first, so that the restructuring work reads as a
reviewable diff against a known starting point. That commit is never pushed and
does not survive into the final history.

## Consequences

- The build configuration is now owned and readable in-repo, at the cost of
  maintaining the plugin list by hand across TanStack Start upgrades.
- Regenerating the lockfile re-resolves every caret range in the manifest and is
  effectively a dependency upgrade. The manifest pins Vite exactly, depends on a
  beta Nitro release, and overrides the bundler version, so this is the most
  likely source of breakage and is sequenced before any file moves.
- Published history restarts. Anyone holding a clone of the old history must
  re-clone; with a single-user private project, that cost is nil.
- Both applications build and test independently. Nothing is shared between them
  at the source level — the only contract is the OpenAPI schema described in
  ADR 0002.
