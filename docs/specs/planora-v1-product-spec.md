# Planora — v1 Product Specification

**Status:** Scope approved for implementation
**Product type:** Private, single-user web application
**Primary AI model:** Kimi-K3 through a configurable OpenAI-compatible API
**Web tier:** TanStack Start (React 19, Vite, Nitro) — SSR application shell, browser-only data access
**API tier:** Python FastAPI, versioned under `/api/v1`
**Data stores:** SQLite in development; PostgreSQL in production
**Repository:** Monorepo — `apps/web` and `apps/api`

> Supersedes the earlier `ai-task-manager-v1-product-spec.md`. Architectural
> decisions are recorded separately in `docs/adr/`.

## 1. Product goal

Build a private task-management web application that combines a three-stage
Kanban workflow with an AI chat assistant. The application should make it fast
to capture an unstructured request, review the fields extracted by AI, manage
the task through completion, and retrieve completed work from an archive.

The v1 product is intentionally single-user. It prioritizes reliable task
capture, clear deadline visibility, explicit confirmation of AI actions, and a
clean path from local development to VPS deployment.

## 2. Success criteria

v1 is successful when the user can:

1. Sign in to the private application.
2. Create a task using either a structured form or natural-language input.
3. Review and correct every AI-extracted field before the task is saved.
4. Move tasks among Todo, In Progress, and Done.
5. Immediately recognize tasks that are due within 24 hours or overdue.
6. Add and render a Markdown note on any task.
7. Use chat to find, create, edit, move, and schedule tasks, with confirmation
   before every write.
8. Find archived tasks by title and restore or permanently delete them.
9. Use the application on desktop and mobile browsers.
10. Deploy the application on a private VPS using Docker Compose.

## 3. Users and access

### 3.1 User model

- v1 supports exactly one private user account.
- There are no invitations, teams, sharing permissions, assignees, or separate
  workspaces.

### 3.2 Authentication

- Login uses one username and password.
- The password is stored only as a strong password hash; plaintext passwords
  must never be stored or logged.
- An authenticated session uses a secure, HTTP-only, SameSite cookie.
- **Single origin.** The reverse proxy serves the web tier and the API tier
  from one hostname: `/api/v1/*` routes to the API, everything else routes to
  the web tier. The session cookie is therefore first-party, CORS is not
  involved, and `SameSite` provides its intended protection.
- **CSRF.** The API rejects state-changing requests whose `Origin` does not
  match the configured application origin. This is in addition to the
  `SameSite` cookie attribute, not a replacement for it.
- The user can change the password from Settings after entering the current
  password.
- A forgotten password is reset with an administrative command run directly on
  the VPS.
- Login attempts must be rate-limited.
- The LLM API key and other secrets remain on the API tier and must never be
  returned to the browser.

### 3.3 Network access

- Initial deployment may be reached by VPS IP during setup and testing.
- Plain HTTP over a public IP is not approved for normal use because it exposes
  login traffic.
- Regular internet use requires a domain and valid HTTPS certificate. The
  reverse proxy must redirect HTTP to HTTPS once the domain is configured.
- Only the reverse proxy exposes public ports. The web tier, API tier,
  scheduler, database, and backup service remain on the private Compose
  network.

## 4. Information architecture

The authenticated application contains:

1. **Active Tasks tab** — the primary three-column Kanban board.
2. **Archive tab** — a searchable single list of archived tasks.
3. **AI chat panel** — accessible from both tabs without becoming a third
   primary tab.
4. **Settings page** — password, timezone, and non-secret LLM connection
   settings.

On desktop, the AI chat panel appears as a collapsible right-side panel. On
mobile, it opens as a full-height drawer or sheet. Closing and reopening it
must preserve the current conversation.

## 5. Task data model

The API wire format is **snake_case**; the TypeScript domain model is
**camelCase**. Conversion happens in exactly one place on the web side (see
§13.3 and ADR 0002).

| Field (wire) | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Generated by the API; immutable |
| `title` | String | Required; concise; editable |
| `content` | Text | Required task description; may be short |
| `status` | Enum | `todo`, `in_progress`, or `done` |
| `category` | Enum | `work`, `personal`, `study`, or `other` |
| `priority` | Enum | `low`, `medium`, or `high` |
| `deadline_at` | Zoned datetime or null | Optional date and time; interpreted in the configured timezone |
| `urls` | List of URL objects | Zero or more links; each has a URL and optional label |
| `markdown_note` | Text | One editable Markdown document per task; empty by default |
| `position` | Ordering value | Supports manual ordering within a Kanban column |
| `created_at` | UTC datetime | Set by the API |
| `updated_at` | UTC datetime | Updated by the API |
| `completed_at` | UTC datetime or null | Set when moved into Done; cleared if moved out |
| `archived_at` | UTC datetime or null | Set by the automatic archive process |

Database timestamps are stored in UTC. The web tier renders and edits them in
the timezone selected in Settings.

## 6. Task creation

### 6.1 Structured form

The structured form provides explicit inputs for:

- Title
- Content
- Category
- Priority
- Optional deadline date and time
- Zero or more URLs with optional labels
- Optional Markdown note

New tasks default to:

- Status: Todo
- Priority: Medium
- Category: Other until selected
- No deadline
- Empty URLs and Markdown note

The user may save without a deadline. Title and content are required.

**Deadline entry is timezone-aware.** The deadline control interprets the
entered wall-clock time in the timezone configured in Settings, not in the
browser's local timezone. A native `datetime-local` input cannot satisfy this
requirement and must not be used for deadline entry (see §12.3, item 2).

### 6.2 Natural-language capture

The application provides a free-text entry mode for statements such as:

> Prepare the search-quality review by Friday 4 PM. Use the experiment
> dashboard link. This is high-priority work.

The API sends this text to the configured LLM and requests a schema-constrained
result containing:

- Generated short title when no clear title exists
- Content
- Category
- Priority
- Optional deadline
- Extracted URLs

The LLM may only propose values. It does not save a task directly.

After parsing, the application always displays an editable preview using the
structured form. The user must explicitly choose **Create task** or **Cancel**.
Validation errors and uncertain or missing fields are shown clearly; the user
is never blocked from correcting the AI.

If AI parsing fails, the original text remains available and the user can
complete the structured form manually.

## 7. Active Tasks tab

### 7.1 Kanban board

The board contains exactly three columns:

1. Todo
2. In Progress
3. Done

Desktop supports drag-and-drop:

- Within a column to reorder tasks manually.
- Between columns to change task status.

Mobile supports touch drag-and-drop where reliable and always provides an
explicit status control as an accessible fallback.

When a task enters Done, `completed_at` is set. When it leaves Done,
`completed_at` is cleared and automatic archival is cancelled.

### 7.2 Task cards

A card shows, at minimum:

- Title
- Category tag
- Priority tag
- Deadline, if present
- Deadline-state indicator
- URL count when links exist
- Note indicator when the Markdown note is non-empty

Selecting a card opens a detail drawer or modal where all fields can be edited.

### 7.3 Deadline states

Deadline state is derived rather than stored. There are **five** states.

| State | Rule | Required visual treatment |
| --- | --- | --- |
| No deadline | `deadline_at` is null | Neutral |
| Scheduled | More than 24 hours remain | Normal deadline treatment |
| Near deadline | Deadline is in the future and no more than 24 hours remain | Amber tag/accent |
| Overdue | Deadline is in the past and status is not Done | Red tag/accent |
| Completed | Status is Done | Completed treatment; never shown as overdue |

`Completed` takes precedence over every other state: a Done task is never
labelled Scheduled, Near deadline, or Overdue regardless of its deadline.

Color cannot be the only signal. Each state must also have text and/or an icon.

v1 provides visual indicators inside the application only. Browser, push,
email, and messaging notifications are out of scope.

### 7.4 Filters

The board supports **combinable multi-select** filters for:

- Category — zero or more of `work`, `personal`, `study`, `other`
- Priority — zero or more of `low`, `medium`, `high`
- Deadline state — zero or more of No deadline, Scheduled, Near deadline,
  Overdue

Selecting nothing within a dimension means that dimension does not filter.
Selections across dimensions combine with AND; selections within a dimension
combine with OR. A clear-all action is required.

The deadline dimension deliberately offers four options rather than the five
states in §7.3. `Completed` is not a filter option, and a Done task matches no
deadline filter: activating any deadline filter therefore hides Done tasks.
This is intended — the deadline filters exist to surface what still needs
attention, and a completed task never does.

Filters affect only the visible board and do not change manual card order.

## 8. Markdown notes and links

- Every task has one Markdown note, editable from its detail view.
- The editor supports Edit and Preview modes.
- Rendered Markdown must be sanitized before display; raw scripts and unsafe
  HTML must not execute.
- v1 does not maintain note versions, comments, or an activity log.
- A task can contain multiple HTTP or HTTPS URLs.
- Links open in a new browser tab with safe link attributes.
- File uploads and attachments are out of scope.

## 9. Completion and archive lifecycle

### 9.1 Automatic archival

- A task remains in the Done column for seven full days after `completed_at`.
- Once seven days have elapsed, a scheduled job moves it to the archive by
  setting `archived_at`.
- The job runs at least hourly, so archival may occur up to one hour after
  eligibility.
- The job runs in a dedicated `scheduler` service, not inside an API worker
  process. In-process scheduling double-fires when more than one worker is
  running; a separate service removes the constraint.
- Archived tasks no longer appear on the active board.
- If a Done task is moved to another status before archival, its seven-day
  timer is cancelled.

### 9.2 Archive tab

- Archived tasks appear in a single paginated list, newest completion first by
  default.
- Search in v1 is case-insensitive keyword/substring matching on title only.
- Search is not semantic and does not search content, notes, or URLs.
- The list displays title, category, priority, completion date, and archived
  date.
- Opening an item shows its complete read-only details.

Available archive actions:

- **Restore:** returns the task to Todo, clears `completed_at` and
  `archived_at`, and places it at the end of the Todo column.
- **Permanently delete:** requires an explicit destructive confirmation showing
  the task title. Deletion cannot be undone through the application.

## 10. AI chat assistant

### 10.1 Allowed capabilities

The assistant can:

- Search and summarize active tasks.
- Search archived tasks using v1's title-search capability.
- Propose creation of one or more tasks.
- Propose edits to task fields.
- Propose movement between Todo, In Progress, and Done.
- Propose setting, changing, or removing deadlines.
- Answer questions such as what is overdue, due soon, high-priority, or in a
  category.

In v1, "schedule" means setting or modifying a task deadline. It does not mean
autonomous calendar planning, time blocking, recurring tasks, or external
calendar integration.

### 10.2 Confirmation model

- Read-only actions and answers do not require confirmation.
- Every create, update, move, restore, archive-related, or delete action
  requires confirmation before the API mutates data.
- The chat displays a structured action-preview card showing the proposed
  changes.
- For edits, the preview shows old and new values.
- The user may confirm or cancel; cancellation performs no write.
- Permanent deletion requires the same stronger destructive confirmation used
  in the Archive tab.
- The API, not the model, validates authorization, field values, task
  existence, and state transitions.

### 10.3 Conversation retention

- The application stores exactly one current conversation.
- The conversation persists across browser sessions and devices.
- Starting a new conversation asks for confirmation and permanently replaces
  the prior conversation and messages.
- Chat history is not an audit log. Confirmed task changes remain reflected in
  task data after conversation replacement.

### 10.4 LLM integration

- The API uses a configurable OpenAI-compatible base URL and model name.
- API credentials are supplied through server-side environment variables and
  are never exposed in Settings responses.
- Structured outputs/tool calls must be validated against server-side schemas
  before use.
- The assistant receives only the minimum task data required to answer the
  request.
- AI errors must result in a recoverable message; they must not partially apply
  mutations.
- No autonomous background agent runs in v1.

## 11. Settings

The Settings page includes:

- Application timezone, selected from IANA timezone names; default
  `Asia/Singapore`.
- Password change form.
- Non-secret LLM settings that deployment policy permits the user to edit, such
  as model name.

Changing the timezone changes both **display** and **future input
interpretation**: a deadline typed as "17:00" after the change means 17:00 in
the new timezone. It does not change the actual instant represented by existing
deadlines.

Secrets, database configuration, and VPS administration are not editable in the
browser.

## 12. Web tier specification

### 12.1 Responsibility

The web tier owns:

- The responsive frontend application and its reusable UI components.
- Typed client-side domain models and UX-level validation.
- A mock API implementation with realistic seed tasks, archive items, chat
  responses, loading states, validation errors, and server errors, used for
  development and tests.
- A single API adapter boundary — the `ApiClient` interface — so the mock
  implementation can be replaced with the FastAPI-backed client without
  rewriting page components.

The web tier does **not** own the database, authentication, LLM integration, or
any authoritative business logic. Its validation exists to give immediate
feedback; the API re-validates everything.

**Data access is browser-only.** The Nitro server renders the application shell
and serves static assets. It does not fetch application data, so there is no
server-side session-forwarding path and authentication has exactly one call
site.

### 12.2 Design direction

- Colorful, modern productivity-app visual language.
- Clear visual separation among categories and priorities without overwhelming
  the task content.
- Amber is reserved for near-deadline emphasis and red for overdue/destructive
  states.
- Responsive desktop and mobile layouts.
- Accessible focus states, keyboard navigation, labels, touch targets, and
  sufficient contrast.
- Support polished empty, loading, error, offline, and confirmation states.

### 12.3 Delivered state and required corrections

A working frontend prototype exists, covering login, the three-column board
with drag-and-drop, the task detail sheet, the structured task form, the
natural-language preview flow, the archive list, Settings, and the chat panel
with action-preview confirmation. It is backed by a mock `ApiClient`
implementation persisting to `localStorage`.

The following divergences from this specification must be corrected:

1. **Filters are single-select.** The board exposes one choice per dimension.
   §7.4 requires combinable multi-select with clear-all, and the "Scheduled"
   deadline option is missing entirely.
2. **Deadline entry ignores the configured timezone.** A native
   `datetime-local` input is parsed in the browser's timezone, violating §6.1
   and §11. Requires a timezone-aware control and an explicit timezone
   conversion library.
3. **The `Completed` deadline state does not exist.** A Done task with a past
   deadline currently reports `Scheduled`. §7.3 requires a distinct fifth
   state.
4. **Production components import from mock fixtures.** The task form pulls its
   ID generator from the seed-data module. Generic utilities must not live in
   dev-only fixtures.

The mock layer and the `ApiClient` interface are retained as specified in
§12.1. The interface itself requires no change to accommodate the API tier —
that is the property acceptance criterion 16 protects.

## 13. API boundaries

### 13.1 Surface

The API is a versioned JSON REST API under `/api/v1`, with a streaming response
mechanism for chat if needed. Exact paths may change during API design, but the
capabilities must include:

| Capability | Suggested endpoint |
| --- | --- |
| Login/logout/session | `/auth/*` |
| Read/update settings | `/settings` |
| Change password | `/settings/password` |
| List/create/read/update tasks | `/tasks` and `/tasks/{id}` |
| Delete active task | `/tasks/{id}` (DELETE) |
| Reorder or change status | `/tasks/reorder` or `/tasks/{id}/move` |
| Parse free text | `/ai/parse-task` |
| List/search archive | `/archive` |
| Restore archived task | `/archive/{id}/restore` |
| Delete archived task | `/archive/{id}` |
| Read/reset conversation | `/chat/conversation` |
| Send chat message | `/chat/messages` |
| Confirm/reject AI action | `/chat/actions/{id}/confirm` and `/reject` |
| Health check | `/health` |

Errors use a consistent machine-readable envelope with a stable `code`, a
user-safe `message`, and optional field-level detail.

### 13.2 Schema sharing

FastAPI's generated `openapi.json` is the single source of truth for the wire
contract. `openapi-typescript` generates TypeScript **types only** into the web
tier; no generated client is used. A hand-written adapter implements the
existing `ApiClient` interface against those types.

CI regenerates the types and fails if the committed output differs from what
the live schema produces, so contract drift is a build failure rather than a
runtime surprise.

### 13.3 Naming

The wire contract is snake_case (§5). The TypeScript domain model is camelCase.
Conversion is confined to a single mapping module in the web tier's HTTP
adapter. No other file converts field names. See ADR 0002.

## 14. Technical architecture

### 14.1 Repository layout

```
planora/
├─ docs/           specs, ADRs, operational runbooks
├─ deploy/         Compose files, reverse-proxy config, backup scripts
└─ apps/
   ├─ web/         TanStack Start application
   └─ api/         FastAPI application
```

### 14.2 Development

- Web tier: TanStack Start with an explicit Vite plugin configuration and a
  Nitro `node-server` build target.
- API tier: FastAPI with SQLAlchemy models and Alembic migrations.
- SQLite database for local development.
- Mock LLM and deterministic fixtures available for tests.
- The same migration history and repository layer must support PostgreSQL
  without application-level model forks.
- The web tier can run against either the mock `ApiClient` or a live API tier,
  selected by environment variable.

### 14.3 Production

Docker Compose runs six services:

1. `caddy` — HTTPS reverse proxy; the only service with published ports.
2. `web` — TanStack Start Nitro server (node target).
3. `api` — FastAPI.
4. `scheduler` — hourly archive job (§9.1).
5. `db` — PostgreSQL.
6. `backup` — daily database backup job.

The proxy routes `/api/v1/*` to `api` and all other paths to `web`, giving the
application a single origin (§3.2).

The database and backup directories use persistent Docker volumes or explicit
host mounts.

### 14.4 Backups

- Run one PostgreSQL backup daily at 03:00 in the configured application
  timezone.
- Retain the latest seven successful daily backups.
- Backups must not contain plaintext application or LLM credentials.
- A documented restore command is required and must be tested before release.
- v1 guarantees rolling local VPS backups; off-site replication is a later
  enhancement.

## 15. Non-functional requirements

### 15.1 Reliability and data integrity

- Mutations are transactional.
- AI-proposed actions are idempotent so retrying confirmation cannot duplicate
  a task or apply an edit twice.
- Reordering persists across refreshes and devices.
- All state-changing API requests require authentication and pass the CSRF
  origin check.
- User-provided Markdown, text, and URLs are treated as untrusted input.

### 15.2 Performance targets

For a personal dataset of up to 10,000 tasks:

- Initial authenticated board load: target under 2 seconds on a typical
  broadband connection, excluding cold VPS startup.
- Normal non-AI mutations: target under 500 ms server response time.
- Archive title search: target under 500 ms.
- AI requests show an immediate progress state and support cancellation; model
  latency is not included in the non-AI targets.

### 15.3 Testing

- Unit tests for pure logic on both tiers. Deadline-state derivation, ordering,
  archive eligibility, and chat-action validation live in dependency-free
  modules specifically so they can be tested directly.
- Integration tests for API endpoints and database operations, run against both
  SQLite and PostgreSQL.
- End-to-end tests for the critical user flows: login, structured creation,
  natural-language capture and confirmation, board moves, archive restore, and
  a confirmed chat write.
- Minimum 80% coverage on both tiers, enforced in CI.

### 15.4 Browser support

- Latest stable Chrome, Firefox, and Safari on desktop.
- Latest stable Chrome on Android and Safari on iOS.
- No native mobile application or installable PWA is required.

### 15.5 Observability

- Structured server logs for request failures, archive jobs, backups, and LLM
  failures.
- Logs must redact passwords, session tokens, API keys, full chat prompts, and
  sensitive task content by default.
- A simple authenticated or internal health endpoint is required for deployment
  checks.

## 16. Explicitly out of scope for v1

- Multiple users, sharing, assignments, teams, or permissions.
- Recurring tasks.
- Subtasks, dependencies, projects, custom tags, or custom categories.
- Browser, push, email, SMS, or messaging reminders.
- Calendar integrations and automatic time blocking.
- File uploads and attachments.
- Semantic/vector search.
- Archive search across content, notes, or URLs.
- AI actions without user confirmation.
- Autonomous background agents.
- Multiple saved chat conversations.
- Note history, task activity history, and audit-log UI.
- Offline editing, real-time multi-device synchronization, and collaborative
  editing.
- Native mobile apps and PWA installation.
- Off-site backup replication.
- Server-side data fetching in the web tier (§12.1).

## 17. Release acceptance criteria

v1 may be considered complete only when all of the following pass:

1. A user can log in, log out, change the password, and reset it through the
   documented VPS command.
2. Structured creation rejects missing title/content and accepts an absent
   deadline.
3. Natural-language capture returns an editable preview and never saves before
   confirmation.
4. AI output cannot create invalid categories, priorities, statuses, or dates.
5. Cards retain manual order after refresh and can move between all three
   statuses.
6. Moving out of Done before seven days prevents archival.
7. A Done task becomes archived after seven days plus no more than the
   hourly-job delay.
8. Near-deadline and overdue states follow the exact 24-hour rules and include
   non-color indicators.
9. Markdown renders safely and malicious HTML/script input does not execute.
10. Filters can be combined and cleared without changing stored task order.
11. Archive title search is case-insensitive and does not claim semantic
    behavior.
12. Restore returns an archived task to Todo; permanent delete always requires
    confirmation.
13. Every chat write shows a structured preview and requires confirmation;
    duplicate confirmations are harmless.
14. Starting a new conversation asks for confirmation and removes the previous
    chat history.
15. The frontend functions at representative desktop and mobile widths.
16. The mock API layer can be replaced by the FastAPI adapter without changing
    page components.
17. Development runs with SQLite; automated tests also run against PostgreSQL
    before deployment.
18. Docker Compose starts the full production stack and exposes only the
    reverse proxy publicly.
19. Daily backup rotation retains seven backups, and the documented restore
    procedure succeeds.
20. No frontend bundle or API response contains the LLM API key, database
    credentials, or password hashes.
21. **Contract integrity.** Regenerating TypeScript types from the live
    `openapi.json` produces no diff against the committed output.
22. **Filter composition.** Multi-select filters combine across category,
    priority, and all four deadline states, and clear-all restores the
    unfiltered board.
23. **Timezone integrity.** A deadline entered as a wall-clock time is stored
    as that instant in the Settings timezone, and remains the same instant when
    the Settings timezone is subsequently changed.
24. **Done tasks are never overdue.** A Done task with a past deadline renders
    in the Completed state in every view.
25. **Dependency provenance.** The lockfile resolves every package from the
    public registry, and no third-party build or telemetry service appears in
    the dependency tree, the served HTML, or the runtime.

## 18. Delivery phases

### Phase 0 — Baseline

- Add `.gitignore` and commit the existing frontend tree unchanged as a local
  staging point, so subsequent restructuring reads as a reviewable diff.

### Phase 1 — Toolchain independence

- Replace the vendored Vite configuration with an explicit plugin list and a
  Nitro `node-server` target.
- Regenerate the lockfile against the public npm registry.
- Remove third-party telemetry and branding from the application shell and
  served HTML.
- Rename the product to Planora throughout: source, CSS class names, storage
  keys, and metadata.
- Verify with a clean install, a production build, and a lint pass.

### Phase 2 — Documentation

- Publish this specification and the architecture decision records.

### Phase 3 — Repository shape

- Move the web application to `apps/web`.
- Scaffold `apps/api` with the module structure below, without business logic.
- Add `deploy/` with Compose files and reverse-proxy configuration.

### Phase 4 — Web reorganization

- Split the web tier into feature modules, shared domain schemas, and the API
  adapter boundary.
- Split the single-file mock implementation by domain.
- Reduce route files to composition only.
- Remove unused UI components and their dependencies.
- Add the unit, integration, and end-to-end test harnesses with the coverage
  gate from §15.3.

### Phase 5 — Specification conformance

- Correct the four divergences listed in §12.3.

### Phase 6 — Core API

- Implement authentication, settings, task model, CRUD, ordering, filters,
  archival, and migrations.
- Replace the mock task/archive/settings adapters with the live client.

### Phase 7 — AI functions

- Add free-text parsing with schema validation.
- Add chat read tools and the confirmed write-action workflow.
- Add failure handling, redaction, and idempotency.

### Phase 8 — Deployment hardening

- Switch production to PostgreSQL.
- Add Compose, reverse proxy, domain/HTTPS, backups, health checks, and restore
  documentation.
- Run security, browser, mobile, and acceptance tests.

## 19. Module structure

### 19.1 `apps/web/src`

```
routes/          thin route shells: layout and composition only
features/        tasks, chat, archive, auth, settings
                 each with components/, hooks.ts, schema.ts
shared/
  domain/        zod schemas and inferred camelCase types
  api/           generated OpenAPI types
  errors.ts      error envelope
services/api/
  ApiClient.ts   the adapter interface — the stable seam
  mock/          auth, tasks, archive, chat, store, seed
  http/          client, mappers, endpoints
components/
  ui/            design-system primitives
  layout/        application shell, navigation, chat dock
lib/             generic utilities
```

### 19.2 `apps/api/src/planora_api`

```
main.py          application factory, middleware, router mounting
config.py        settings; fails fast when required secrets are absent
api/v1/          auth, settings, tasks, archive, ai, chat — thin routers
schemas/         pydantic wire contract
domain/          pure logic: deadline, ordering, archive policy, chat actions
db/              session, models, repositories
ai/              client, parse_task, chat_tools, redact, prompts
jobs/            archive_done_tasks, scheduler
security/        password, session, rate_limit, csrf
logging.py       structured logging with redaction
```

`domain/` contains no I/O. Deadline derivation, ordering, archive eligibility,
and chat-action validation are pure functions, which is what makes the
acceptance criteria in §17 items 6–8 and 24 directly testable.

## 20. Known risks

**Lockfile regeneration is a de-facto dependency upgrade.** Discarding the
existing lockfile re-resolves every caret range in the manifest. The tree pins
`vite` exactly, depends on a beta `nitro`, and overrides `rolldown`. This is
required work, but it is the most likely source of breakage in Phase 1 and
should be verified by a clean install plus a production build before anything
else proceeds.

**The Vite configuration replacement is reconstructed, not copied.** The plugin
set was derived from the lockfile's peer dependencies and the vendored config's
own documentation rather than from installed sources. The first successful
production build is the verification gate. A shortfall there is a bounded
debugging task, not a design change.

**Both risks land in Phase 1 deliberately** — before 79 files move — so that a
toolchain problem surfaces while the tree is still in its original shape.

## 21. Later-phase candidates

Potential follow-up work, not committed for v1:
